# Classic Checkpoint Semantics

## Scope

This document defines MALBODOOM TARGET_B2 checkpoint behavior. It is a design
contract, not proof that `program_v1.mal` exists. Claims remain
`NOT_DEMONSTRATED` until a fixed Classic artifact performs these operations.

## The Password Model

Like a cartridge-game password, a continuation anchor is a portable sequence
of bytes. A player can save it, close the process, start a new ordinary
Classic VM later, paste it, and continue according to the declared mode.

The anchor is **data**, not a replacement `.mal` program:

```text
same frozen program_v1.mal + N + input          -> first epoch
same frozen program_v1.mal + R + anchor + input -> resumed epoch
```

The same `program_v1.mal` SHA256 must be used for every input, death,
checkpoint and interpreter. Generating a state-specific `.mal` program would
violate `COMPILE_ONCE_TEST_MANY` and is not this design.

## The 59049 Rule

Classic has 59049 memory words. It does **not** have a natural 59049-step
limit: a program may execute more or fewer steps without allocating more
memory. Therefore checkpointing cannot honestly mean "every 59049 steps".

Each VM uses a Malbolge-owned managed budget:

```text
program + active state + temporary workspace <= HIGH_WATER
checkpoint reserve = encoder + decoder + stream workspace
HIGH_WATER + checkpoint reserve <= 59049
```

Only the Classic program may decide that its managed live state reached
`HIGH_WATER`. The host may measure steps for evidence, but must not use that
measurement to request, force, defer, or construct a checkpoint.

## Mode 1: Anchor Continue

Use this when the game has not ended but the managed memory budget is reached.

```text
PLAYING
  -> Malbolge observes managed HIGH_WATER
  -> stop admitting new work
  -> canonicalize declared persistent state
  -> stream MBD1A anchor bytes
  -> emit ANCHOR framing
  -> HALT
  -> fresh Classic VM receives R + exact opaque anchor + next input
  -> Malbolge validates, decodes and resumes
```

Required semantic property for the declared state projection:

```text
canonical(next_without_restart) == canonical(next_after_anchor_resume)
```

The old process must be dead before the next process starts. No snapshot,
shared memory, VM object reuse or host-side state reconstruction is allowed.

## Mode 2: Death Continue Or Rebirth

Death is a second, game-defined checkpoint point. Malbolge detects the death
condition from its own game state; the host does not infer it from a frame,
input or timer.

```text
DEAD
  -> CONTINUE: emit exact continuation anchor, HALT, fresh VM resumes exactly
  -> REBIRTH: derive declared seed inside Malbolge, discard declared transient
     state, emit compact death anchor, HALT, fresh VM starts the rebased state
```

`CONTINUE` is exact under the declared canonical projection.
`REBIRTH` intentionally is not exact resume. It must state exactly which
fields are discarded, regenerated or derived.

## Anchor Ownership

For V1 the fixed-width toy framing is:

```text
MBD1A-<epoch><logical-2trits><acc><rng><local><check>\n
```

All of the following must execute in Classic Malbolge:

- checkpoint/death decision;
- canonicalization;
- payload encoding;
- integrity calculation;
- prefix, payload and integrity validation;
- payload decoding;
- state transition and rebirth-seed derivation.

The host is only a byte cable: launch, pipe input, capture output, store the
anchor byte-for-byte, feed it to a fresh process, present a framebuffer, and
record PID/timing/hashes. A host may hash an anchor for evidence but may not
parse fields or let that hash influence the candidate.

## Evidence Gates

The first acceptable V1 artifact must prove:

1. Same artifact SHA over multiple runtime inputs and epochs.
2. Malbolge-owned `HIGH_WATER` branch, not a host step counter.
3. Malbolge-owned anchor encode, decode and checksum rejection.
4. At least three fresh VM boundaries with distinct dead PIDs.
5. Exact continuation against a declared reference projection.
6. `CONTINUE` and `REBIRTH` produce distinguishable, specified results.
7. Cross-interpreter handoff: `gost -> oracle` and `oracle -> gost` using
   an anchor generated by the candidate.

Until all gates pass, use `CLASSIC_ANCHOR_PRIMITIVE_NOT_DEMONSTRATED`.
